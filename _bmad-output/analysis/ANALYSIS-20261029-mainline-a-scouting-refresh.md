## 3. 第二遍：论文核对与接口反证

### 3.1 论文实际支持什么

- 论文 §2.1、§3.1 明确支持轻量元数据与完整正文的双重表示，以及依赖、继承、调用三层关系图；§3.2 支持先侦察再读取正文。[原始论文提取行 198～215、270～318](../../docs/references/FastCode-arXiv-2603.01012v2.pdf:198)
- 论文 §3.3 采用动态行数预算，而非本项目的 UTF-8 字节预算；预算随问题复杂度与仓库复杂度变化。论文没有规定本项目必须使用 100 KB 正文、150 KB POST，也没有证明 81 个文件解析或全预检能在 2 秒完成。[原始论文提取行 450～594](../../docs/references/FastCode-arXiv-2603.01012v2.pdf:450)
- 论文公式 (1) 为相关性减成本的上下文选择目标；公式 (2) 为相关性、工具发现标记、细粒度密度的加权优先级，并按预算贪心保留。论文没有在该段提供可直接照搬的权重。[公式 (1)](../../docs/references/FastCode-arXiv-2603.01012v2.pdf:216)、[公式 (2)](../../docs/references/FastCode-arXiv-2603.01012v2.pdf:574)
- 本项目采用的 1～2 跳导航、98,304 正文字节和 150,000 POST 字节是本次工程适配约束，不冒称论文固定参数。[参考说明中的工程映射](../../docs/references/README.md:16)只能作为二手索引，不能覆盖原文。
- 论文还使用混合检索、LLM 增强和迭代置信度控制；本阶段只借鉴本地侦察与成本选择，不增加外发轮次，不伪造自评置信度。论文附录的实例类型推断也不是当前实现已具备的能力。[论文附录 A.1](../../docs/references/FastCode-arXiv-2603.01012v2.pdf:1161)

### 3.2 为什么不能只删全量必需组

- [正文包构建](../../src/solo_distill/package_v2.py:22)会补齐条件来源、合并包含所有者，并只注册所选所有者覆盖的语法单元；因此单纯缩小所选单元会同时缩小包内结构分母。
- [包校验器](../../src/solo_distill/package_v2.py:204)要求每个包内单元有对应 source 和合法 owner；不能直接给单元附空 owner，或任意增加 metadata-only 字段来保持表面兼容。
- [adaptive 核心封装](../../src/solo_distill/core_v2.py:334)保留所有表并核对关系完整性；[生产消费端](../../src/solo_distill/consumer_v2.py:153)要求包内语法单元集合等于原始来源全量集合。[独立接收器](../../tests/adaptive_receiver.py:98)也检查定义分母及逐调用/导入位点，不只是抽样函数。
- [现有调度器](../../src/solo_distill/scheduler_v2.py:137)在 adaptive mandatory 中不执行正文硬限制；其 optional 路径仍有 32 块、pipeline 配额和每文件限制。[optional 选择](../../src/solo_distill/scheduler_v2.py:221)不是本次新的问题优先级与字节预算算法，不能简单“恢复旧调度”并宣称兼容。
- [现有关系提取器](../../src/solo_distill/graph_v2.py:143)主要产生调用和导入位点；模块导入保留未知，实例属性分派保留未知。虽然[图查询接口](../../src/solo_distill/graph_v2.py:188)允许 inheritance 名称，但当前提取路径未实现论文的完整三层已解析图。
- [现有专用驱动](../../verification/.scratch/mainline_a_20261029.py:330)只接受 health 和 preflight；原计划列出的 live、reconcile 入口尚未在该驱动实现。旧在线驱动仍按总响应 22,016 字节拒绝大响应，并保留 210 秒清理窗口，不能作为本轮分片与 180 秒生命周期的直接入口。[旧驱动](../../tests/live_v2_driver.py:148)

## 4. 硬门禁筛选与最小充分裁决

| 候选 | 门禁裁决 | 原因 |
| --- | --- | --- |
| 提升网关上限或利用 stdio 分片解决 HTTP 上行 | 排除 | 改变物理契约，且下行分片不减少上行请求体 |
| 保持全部 mandatory，只分页展示骨架 | 排除 | 已证实完整正文自身就超过网关上限 |
| 缩小 include 或切回 legacy | 排除 | 违反全量来源分母与显式传输契约 |
| 只删必需组，将选中局部包直接交给旧 adaptive consumer | 排除 | 静态检查已发现分母接口不兼容 |
| 新建“全量 metadata + 少量 body”公开知识包版本 | 条件可行，但非首选 | 需同步包格式、摘要、切片、封装、两个消费端及版本分发；扩大本轮改动面 |
| 保持既有完整公开静态包，单独选择有限 Prompt 正文 | 推荐，条件可行 | 直接解除结构分母与模型正文的绑定，保留已有消费与认证形状；仍须优化本地重型构建并实测 |

本阶段选择最后一项，不编造质量评分。完整静态包仍只含身份、坐标、成本、条件和关系等注册记录，源码全文留在本地来源快照；完整 owner 记录的成本不意味着该正文必须发送给模型。[包内 owner/source 形状](../../src/solo_distill/package_v2.py:60)、[核心封装形状](../../src/solo_distill/core_v2.py:49)

## 5. 具体调度与架构修正方案

### 5.1 三个视图，各司其职

1. 全量侦察索引：本地保存全来源哈希、全部单元坐标、签名、必要注释、条件、调用/导入位点、解析状态及未知关系；不把全库索引或全量单元 ID 清单放入 Prompt。
2. 完整静态知识包：保持现有 V2 包全部结构分母、owner/source 关联与封印契约，供本地核验及既有下行分片消费。它不是“所有正文必须被模型读取”的证明。
3. 问题正文视图：独立存放选中的完整单元、包含合并后的唯一正文、合法别名 source ID、命中维度、拓扑路径、成本与省略原因。只此视图生成模型输入；其选择收据保存在本地，不另建任务进度账本。

优先复用既有 V2 包形状，不给公开包增加未知字段。若将来要求下行公开携带全库签名/注释或选择收据，应另行评审版本化扩展；本阶段本地侦察索引不自动改变消费者契约。

### 5.2 本地索引与可信导航

- 保留完整扫描、秘密字面量检查、源版本验证。一次快照内按内容哈希与解析器版本复用不可变 AST、坐标、单元和条件索引；共享 AST 不执行、不修改目标代码。[当前证据读取](../../src/solo_distill/evidence_v2.py:82)、[语法提取](../../src/solo_distill/syntax_v2.py:73)
- 每个维度分别从问题抽取标识符及当前词族，匹配限定名、签名、文件名和 docstring；匹配记录可追溯，不使用独立验收资产的 expected 文本、行号或隐藏锚点。[当前词族处理](../../src/solo_distill/live_v2.py:56)
- 以强匹配和静态入口登记为种子，默认沿已解析调用/依赖边展开 1 跳；未覆盖问题所要求的调用方、被调用方、状态写入或失败边界时，最多补第 2 跳。继承边仅在存在可验证基类唯一解析时使用。
- 扩展是候选发现，不是正文依赖闭包：不能把每条调用边都变为必需正文。双向邻接只用于需要调用方的维度；文件级导入只发现候选文件，不能自动提升为该文件全部函数。
- 第一版可新增本地导航专用模块映射和保守作用域类型推断；不更改现有认证关系记录的含义。对构造初始化唯一绑定可记录可审计导航路径；重绑定、条件赋值、动态 getattr、外部模块及多目标分派保持未知，不能以同名方法制造确定边。
- 若实例分派尚未支持，允许以接收者名称与方法名作低置信词法候选，记录“词法补充、未证明调用目标”。关键路径仍不明时阻塞该维度，不能声称纯调用图已定位全部链路。
- 在高出度节点按上述证据优先级有界访问；拟议保护上限为 256 个候选单元、2,048 条扩展边。达到上限记录探索不完整；这些是评审参数，不是已实测最佳值，必需证据受影响时不得通过。

### 5.3 可解释优先级与贪心配额

论文的加权公式提供思想，但本项目当前没有权重标定证据。第一版采用确定性分层排序，不宣称有概率意义或最优性保证：

1. 先保留四维问题明确要求的证据义务：入口与主要分支；状态写入及调用方/被调用方；失败及上下文边界；来源范围、解析与验证盲区。义务按问题生成，不按全库单元生成。
2. 对每项义务列候选完整单元及可解释来源；优先精确签名/标识符匹配，再考虑可信图邻居，再考虑 docstring/文件名匹配及未解析词法补充。用稳定路径、字节范围和单元 ID 解同分。
3. 在上述同一证据层级内，优先补足尚未有直接正文的维度，然后按“新增匹配问题信号数 / 新增唯一完整正文字节”排序，再以跳数及稳定定位解同分。计数来自实际命中，零新增正文成本的真实包含别名先去重，不做除零运算。
4. 先选择最小候选证据组并保留必要的条件来源闭包；组内必须同时计入所要求的调用方/被调用方。若最小必需组不适配正文或 POST 预算，返回明确阻塞，不删除必需证据。
5. 再按四维轮转填充可选候选。每次以候选组的增量唯一正文及实际序列化增量检查配额，放不下则记录省略原因并检查后续更小候选；没有正增益或预算耗尽即停止。
6. 最多进行有界的候选替代；达到状态/候选限制是 search_exhausted，不是 capacity_proven。贪心失败不证明所有组合都不可行，应交付当前候选范围与缺口。

不要通过修改全局 telemetry 策略或 legacy 32 块配额来实现上述算法。拟议独立问题选择器消费轻量索引；[当前选择入口](../../src/solo_distill/live_v2.py:107)协调完整静态包与 Prompt 视图，[现有 Scheduler](../../src/solo_distill/scheduler_v2.py:82)旧语义及其他调用方保持不变。

### 5.4 完整代码单元、别名与模型证据边界

- 默认选择完整函数/方法、相关顶层语句或必要条件来源，不因要一个方法就发送整个类。选中父单元确实完整覆盖子单元时才合并成本；严格按语法路径、同文件及字节包含判定。[现有包含与坐标依据](../../src/solo_distill/package_v2.py:16)
- Prompt 的正文所有者是“选中完整单元的包含合并”，不是完整静态包中所有 owner 的遍历。方法可从本地坐标独立取完整正文，即使其公开 source 在全量包中归属一个类 owner；公开包关联无需改写。[正文提取](../../src/solo_distill/syntax_v2.py:134)
- 别名只列被发送正文真实完整包含且本次允许引用的 source ID；不能沿用全库 owner 的所有别名，把未发送的方法或整个类伪装成已消费。
- [候选结论合并](../../src/solo_distill/live_v2.py:166)当前只检查 source ID 是否存在于全包。拟议新增 Prompt 来源 allowlist 校验：模型不能引用未发送单元，即使它存在于完整静态包；未知引用、跨快照引用及伪造别名一律拒绝。
- 静态关系可证明源码中存在调用位点，不能证明调用实际执行、返回值被处理或持久化成功；[四维参考验收](../../tests/fastcode_acceptance.json:3)继续由独立消费侧保管，不能进入生成选择。

### 5.5 双层字节门禁与同一序列化路径

- 正文硬预算采用 98,304 字节，低于十进制 100 KB。累计的是唯一被发送完整正文转换后的 UTF-8 字节，不能直接用原始编码字节跨度，也不能重复计别名。
- POST 新验收门禁采用十进制 150,000 字节。它指现有网关检查的 HTTP 请求体，含 model、messages、stream、系统提示、问题、维度、局部必要元数据、来源 ID 和两层 JSON 转义；不把 HTTP 头部计入该既有请求体门禁。[真实序列化](../../src/solo_distill/gateway.py:87)
- 98,304 字节正文不自动保证 150,000 字节 POST：引号、反斜杠、非 ASCII 文本、别名及元数据会改变编码长度。不得用本次 1.55 MB 的放大比例外推保证。
- 将确定性请求体编码提取为无网络副作用的共享入口，预检与实际发送均使用完全相同的消息构造、序列化参数及编码；拟议调整限于[网关编码位置](../../src/solo_distill/gateway.py:87)及[模型输入组装](../../src/solo_distill/live_v2.py:302)，网关 393,216 字节硬限制和单次发送行为不变。
- 每个候选组准入均核对正文成本和共享编码后的 POST 成本。可先计算精确单源编码增量，最终必须编码完整实际请求体；只淘汰可选候选，不截函数、删除分支、删除条件或缩小来源分母。
- 固定系统/问题元数据自身超过新门禁、单个必需函数过大、必要条件来源膨胀或必需组超限，都在建连前阻塞。不得因尚小于 393,216 字节就绕过本草案 150,000 字节验收。
- 下行继续使用显式 adaptive 分片：单帧不超过 22,016 字节，累计传输和解码各不超过 4,194,304 字节，最多 256 通知分片及唯一最终清单；计入实际封装与 base64 成本，不预设全量结构必然适配。[独立分片接收检查](../../tests/adaptive_receiver.py:36)

## 6. 预检超时修正与优化预期

### 6.1 已识别的静态热点

- [当前预检](../../verification/.scratch/mainline_a_20261029.py:240)先取 inventory，再调用会再次取 inventory 的[选择入口](../../src/solo_distill/live_v2.py:114)，存在同次预检重复读取与提取。
- [角色提取](../../src/solo_distill/evidence_v2.py:18)每单元解析整文件；[角色附着](../../src/solo_distill/evidence_v2.py:50)和[直接角色验证](../../src/solo_distill/package_v2.py:237)重复调用它。[包校验](../../src/solo_distill/package_v2.py:167)还反复重建全文件单元。
- [包所有者合并](../../src/solo_distill/package_v2.py:41)及[调度所有者合并](../../src/solo_distill/scheduler_v2.py:115)有集合内部成对包含比较。[关系条件匹配](../../src/solo_distill/graph_v2.py:170)逐关系扫描条件表。
- 全量必需组只有一个候选组合，不能把本次超时武断描述为指数级组合爆炸。缺乏阶段实测时，以上是源码风险定位，不是耗时占比结论。

### 6.2 优化修改点

1. 预检、完整包构建和问题选择共享同一经验证快照；不得重复 inventory。完整新运行仍重新验证原始来源，不复用历史“绿灯”。
2. 每文件一次语法解析与作用域遍历，生成路线到 AST 节点、ID 到单元、父子包含、条件前缀和角色信号索引；校验缓存按内容哈希、解析器与规则版本绑定，且不能让调用方注入已通过标志。
3. 用语法树父子索引或区间层级处理包含与别名，避免全量成对扫描；按文件/语法前缀索引条件；用 ID 映射替代单元表线性查找。
4. 全量结构图仍本地构建，但 Prompt 闭包只处理有限候选及必要语法支持，不运行全库 mandatory 正文调度。完整公开包认证不因性能优化删除检查。
5. 每阶段记录扫描、索引、候选发现、选择、完整包认证、POST 编码、来源复核与保存耗时；记录解析调用次数、候选数、边访问数和超时阶段。有界进度先保存，外层 124 无最终回执不能记通过。

### 6.3 可验优化目标，而非效果承诺

| 项目 | 历史证据 | 拟议目标与门禁 |
| --- | --- | --- |

## 9. 第三遍：反向审查与停止条件

- 若只做 Prompt 剪枝而全量包仍反复解析，容量可改善但预检仍可能超时；因此索引/校验复用与阶段剖析是同阶段必要项，不以压缩字节冒充性能通过。
- 若完整静态下行封装超 4 MiB，首选方案仍应阻塞；不能压低分母或偷偷引入新包版本。公开 metadata-only 包是后续独立评审候选，不自动切换。
- 两跳不足以支持跨层结论时，可在同一允许范围内针对已明确缺口补选候选，但不能无限拓展；上限内仍缺必需证据就返回 unknown/blocked，不做额外 POST。
- 贪心与精确字节门禁不能证明四维语义充分；必须保持独立验收资产、原始生成内容和人工语义复读，尤其不得把存在 source ID 当作模型实际读到该代码。
- 本地快照缓存不能跨变更继续使用；源复核、封印和消费端独立核验不能因优化删掉。静态角色标签不证明运行所有权。
- 旧计划仍包含全量必需正文与自动归档历史条款。本补充不静默覆盖该文件；评审批准后由工程显式修订绑定契约，保留旧未完成事项，并重新取得相应执行授权。

最小充分裁决：推荐“完整本地静态分母/既有下行包 + 有限问题 Prompt 视图 + 精确 POST 双门禁 + 单快照索引复用”。现有证据足以支持此方向进入评审，但不足以证明优化后性能、完整分片或四维语义验收通过。草案保持 PROPOSED；当前执行保持 BLOCKED，本轮文档交付后暂停等待人工评审。
